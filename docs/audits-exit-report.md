# Audits module — exit report

**Date:** 2026-11-08 · **Plan:** `docs/audits-plan.md` (§7–§11) · **Gap analysis:** `docs/audits-spec-gap-analysis.md` · **Slices:** AU1 definitions, AU2 schedule, AU3 records, AU5 response types, Phase A findings and promotion to a non-conformance · **Branch:** `Dev`

## What was built

Documentation → Audits, Audit schedule, Audit records and Audit findings, plus Settings → Audits.

- **Definitions (AU1).** A quality team defines an audit: title, type, purpose, procedure, frequency (daily to yearly, every N days, on demand) with first due date, grace days and weekdays-only, the expected auditor (shown, not enforced), a pass mark, a checklist, and what it is relevant to (machines, operation codes, departments). Retired with a reason, never deleted. Editing is free and audited; records keep a frozen copy.
- **Schedule (AU2).** One slot per audit per due date, generated by the API when the schedule or register is read (no worker). Done, overdue and missed are worked out, never stored. Slots can be skipped with a reason and put back. Figures (due soon, in progress, overdue, missed, done, pass rate, on-time rate), list and month calendar.
- **Records (AU3).** Starting an audit freezes its title, procedure, pass mark and checklist into a record (`AR-YY-NNNN`). The person records which of the listed machines/operations/departments it was carried out on. **Every write is a database function**; the database works out each answer's result and the overall result (fail if any critical question failed or the score is below the pass mark). A completed record is frozen; a "still needed" list says what is missing.
- **Response types (AU5).** The template sets how each question is answered, and the record form shows exactly that control: yes/no, compliant/non-compliant, pass/fail, yes/no/N-A, numeric, text, multiple choice, measurement, evidence (file needed to complete), rating. Evidence files go to the private `audit-files` bucket and are never deleted, only removed with a reason.
- **Findings (Phase A).** A failed answer can become a finding (`AF-YY-NNNN`) with a classification the organisation manages (major / minor non-conformity, observation, opportunity), owner, due date and evidence. **A failed critical answer needs a finding before the audit can be completed.** A non-conformity finding is raised as a draft non-conformance on request, once (idempotent), with source *Internal audit*; the NC page shows the source audit, answer and evidence.

## Design notes

- **Nothing is stored that can be worked out.** Done, overdue, missed, the next due date and the result are computed, so they cannot drift.
- **Frozen on start.** A record never changes when the definition is later edited; the definition is not versioned (decision A5), the record is the evidence.
- **Findings are explicit, never silent.** An NC is never raised without a person asking; asking twice returns the same NC. A finding with a live NC cannot be withdrawn or closed until the NC is closed.
- **Source and category on the NC.** Since the NC category/source work, audit-raised NCs carry source *Internal audit*. Audit-raised NCs that existed before were moved to that source by the backfill (the live project has none). The category is left for the person (the NC cannot be opened without one).

## Limits — not built, and not verified

- **No worker.** Slots are generated when read; nothing sends a reminder. No email or push; no menu count of overdue audits (the schedule shows them).
- **Not built (later phases of the gap analysis):** repeat-finding link, several answers on one finding, reviewer approval and auditee acknowledgement (Phase B), templates with versions (C), a criteria library (D), programmes and an audits dashboard (E), notifications for findings, files on the procedure, corrections to a completed record (a new record is the correction), external or customer audits with certificates, scoring weights, auditor competence checks.
- **The journey does not cover:** skipping and putting back a slot, the month calendar, retiring an audit, uploading an evidence file in the browser, the findings register and its filters, withdrawing or closing a finding, Settings → Audits, or an audit with no machines listed. These are covered by component and API tests only.
- **Live data is thin.** The live project holds one audit definition, one record and no findings (test data). The findings and evidence-file paths have been exercised on a throwaway database, not against live data or the real storage bucket.
- **Accepted equivalent mutants** (plan §7): the service's own forbidden check and organisation filter on load (the guard and row-level security already answer), and the form clearing "critical" twice when a question becomes a note. Mutation counts for the AU2 and AU3 migrations were not recorded; their SQL tests passed but were not separately mutation-checked in this exit check.
