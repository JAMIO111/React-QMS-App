# Fortress QMS — project audit (10 November 2026)

Scope: frontend (`src/`), API (`api/`), database (`supabase/migrations/`), at `Dev` commit `a2221ee`.
No application code was changed. Nothing was pushed.

## How to read this

- **Checked** means I ran it: against a throwaway Postgres with all 100 migrations applied, signed in as
  different roles, or against the real API started on that database.
- **Read** means I found it in the source and did not run it.
- Coverage is risk-based, not exhaustive. Tenancy, permissions, billing, NC, calibration, members and the
  cross-module links were probed directly. CAPA, audits, supplier quality, inspection, SPC, integrations,
  custom fields and documentation were covered by catalogue checks (every table, grant, policy and function)
  and targeted probes, not by walking every screen. No browser session was run. The repo's own full test
  suites were not re-run as a baseline.

## Summary

| Severity | Count | What it means |
| --- | --- | --- |
| Critical | 0 | No way was found for one organisation to read or change another's data, or for a person to give themselves rights. |
| High | 6 | Wrong quality outcomes or duplicated records that a normal user can cause. |
| Medium | 14 | Real bugs or hardening gaps with limited reach. |
| Low | 10 | Hygiene. |

The security structure is sound. Most of the findings are business rules that stop too early.

## 1. What held up (checked)

- Every public table has row-level security and policies. No view lacks `security_invoker`. No public-schema
  function is callable by `authenticated` or `anon`.
- Cross-organisation reads and writes were refused everywhere I tried: NCs, costs, audit trail, outbox,
  notifications, supplier performance, custom values, the API with another organisation's id (404).
- A viewer or admin cannot raise their own rights: an admin cannot assign Owner to themselves, nobody can
  write `platform_admins`, subscriptions, `billing_required`, `entitlements_enforced` or call `app.stripe_*`.
- The API rejects unsigned tokens (`alg: none`), malformed organisation headers, SQL in `sort` and `q`.
- An attachment record needs a real stored file inside that record's own folder.
- All nine storage buckets are private.
- Stripe webhook: signature verified over the raw body; refuses without a secret (503).
- Cron routes: constant-time secret check; 503 when no secret is set.
- Integration credentials are held in Supabase Vault; only the API login can read them back.
- The REST connector's outbound client blocks private addresses, pins the checked address and never follows
  redirects (read, plus its unit tests).
- `qms_api` is not a superuser and does not bypass row-level security.

## 2. High

### H1. One failed calibration can raise several NCs (checked)
Four simultaneous `POST /calibrations/{id}/raise-ncr` calls returned 201, 409, 201, 201 and left **three** NCs.
`calibration-records.service.ts` reads `nonconformance_id`, then inserts, with no lock. A double click is enough.
**Fix:** `SELECT … FOR UPDATE` on the calibration row first, or a unique index on the link.

### H2. A calibration with only some readings counts as a pass (checked)
A gauge with three characteristics and one in-tolerance reading is worked out as "pass" and a quarantined
gauge goes back to active. **Fix:** require a reading for every active characteristic before an outcome.

### H3. A failed calibration reading can be rewritten to a pass later (checked)
Someone with `calibration.record` only (an inspector) can edit an old failed reading; the outcome flips and
the gauge is reinstated. There is no lock, approval or reason. **Fix:** freeze a calibration once saved, or
require `calibration.manage` and a reason for corrections, as inspection measurements already do.

### H4. NC stage gates can be emptied after opening (checked)
After an NC is opened, severity, quantity affected and description can be blanked. With no quantity the
disposition gate passes, and containment can be waived with the reason "n/a". Result: an NC taken from Open
straight to Closed with no severity, no quantity and no disposition. **Fix:** keep the "needed to open"
fields non-empty past draft; require a quantity (or an explicit "not applicable") before Dispositioned; a
minimum length on the waiver reason.

### H5. Site-limited people see an empty app (checked)
`GET /me` returns `permissions: []` for someone whose only role is limited to a site, while the API lets them
list gauges (200) and create an NC at their site (201). The menu and buttons hide almost everything.
`app.my_permissions` counts organisation-wide assignments only. **Fix:** return the union of permissions held
anywhere, and let the server keep deciding per site.

### H6. Changing the base currency mixes currencies in totals (checked)
Existing cost lines keep the old base currency. The register adds `gross_base` across them and labels the sum
with the new one (GBP 100 + EUR 115 shown as "215 EUR"). **Fix:** refuse the change once costs exist, or
store the base currency per total and convert.

## 3. Medium

### Security and hardening

- **M1. API docs are public (checked).** `/api/v1/docs` and `/api/v1/openapi.json` answer 200 with no token:
  the full route map, including internal ones. Put them behind auth or switch them off in production.
- **M2. No security headers (checked for the API, read for the web app).** The API sends no
  `Strict-Transport-Security`, `X-Content-Type-Options` or `X-Frame-Options`; `vercel.json` sets none for the
  frontend and there is no Content-Security-Policy. Add `helmet` and a `headers` block.
- **M3. An oversized request returns 500 (checked).** A 2 MB JSON body gives `500 internal_error` instead of
  413. It also fills the error log with false alarms.
- **M4. Rate limiting is likely ineffective on Vercel (read).** No `trust proxy`, so the limiter sees the
  proxy's address, and the counter is in memory per instance.
- **M5. Leaked-password protection is off on the live Supabase project** (Supabase advisor).
- **M6. Old secrets in git history (read, from earlier in the session).** An early `.env` commit holds an anon
  key for a previous Supabase project and a UniRate API key. `VITE_UNIRATE_API_KEY` is also still read by
  `src/api/uniRateExchangeApi.js`, so it ships in the browser bundle if set. Rotate the UniRate key; delete
  the file if unused.
- **M7. Helper functions answer for any organisation (checked).** `app.ncr_gate_problems`, `app.ncr_site`,
  `gauge_site`, `calibration_site`, `inspection_site`, `check_entitlement` and `organisation_access_state`
  are SECURITY DEFINER with no caller check. With another organisation's record id they return its gate
  problems (including lot numbers and quantities) or site id. Ids are random UUIDs, so reach is small.
- **M8. A locked organisation can still read master data (checked).** With the billing gate on and no valid
  subscription, members can still read parts, revisions, customers, suppliers, machines, gauge types, sites
  and settings directly. Writes are blocked.

### Bugs

- **M9. A removed member can never rejoin (checked).** A new invitation is created and shown, but accepting
  fails with "already a member". The API has no removed → active path.
- **M10. Member status rules live only in the API (checked).** Someone with `members.manage` can set
  statuses directly through Supabase that the API forbids (removed → active, active → invited).
- **M11. Settings → Account is a mock-up (read).** Personal details are not saved; **Change Password** and
  **Delete Account** have no handler; the three password boxes are plain text, not masked.
- **M12. People from outside the organisation can be assigned (checked).** NC owner, NC "detected by" and
  gauge custodian accept a user id from another organisation, and a removed member can still be assigned.
- **M13. Deleting an NC linked to a running 8D leaves the link live (checked).** Closing is blocked while an
  8D runs; soft-deleting is not, and the 8D keeps pointing at a deleted NC.
- **M14. Dates use UTC (read, from earlier in the session).** "Not in the future" checks use the database's
  `current_date`; `sites.timezone` is unused. A user ahead of UTC can be refused today's date.

## 4. Business-logic gaps between modules (all checked unless noted)

| Area | What happens today | Why it matters |
| --- | --- | --- |
| Supplier approval → purchasing | Purchase orders and goods receipts are accepted for a **pending** or **disqualified** supplier. | Approval status has no effect on buying. At least warn; ideally block disqualified and suspended. |
| Receiving | 1,000 units received against an order line of 10, no warning. | Skews on-time, in-full and PPM figures. (Listed as "not built".) |
| Lots ↔ NC | A lot on hold can be released or closed while an open NC names it. | Suspect material can be released. |
| Production order ↔ NC | An order can be completed with an open NC against it. | Same. |
| Lots ↔ orders | A lot of 5,000 on an order planned for 10; serial numbers not capped by lot quantity. | Traceability quantities cannot be trusted. |
| Inactive master data | New production orders and NCs accepted on an inactive part; an NC can name an inactive customer; a supplier with open orders can be deactivated. | "Inactive" only hides records from pickers. |
| Gauges | Quarantine can be lifted by hand with no reason and no new calibration; next due can be set 30 years out; adding a type to an existing gauge copies no characteristics; a manual next-due is overwritten by any later edit of the latest calibration. | Weakens calibration control. |
| NC | `detected_at` can be far in the future; a 2 MB description is accepted directly (the API caps 5,000). | Limits exist only in the API. |
| Leavers | Removing a member leaves them as owner of open NCs with no prompt to reassign. | Work is orphaned. |

## 5. Low

- `role_permissions` has an UPDATE grant with no UPDATE policy (dead grant).
- `authenticated` holds DELETE on control-plan content, `part_customers`, roles and role assignments. Policies
  blocked a viewer in every case tried; worth a review against the "nothing is deleted" rule.
- File buckets for NC, calibration, CAPA, alerts, audits and suppliers accept any file type; `org-logos`
  accepts SVG. Files are served from Supabase's domain through signed links, so script risk to the app is low.
- 174 objects are visible in the GraphQL schema to signed-in users (Supabase advisor; RLS still applies).
- Invitation matching uses the account's email without checking it is confirmed. Safe while email
  confirmation stays on in Supabase Auth; do not turn it off.
- Dead code calling Supabase directly: `src/api/supabaseApi.js` (`get_nc_kpi_json`, `get_nc_date_trend`,
  generic insert), `useSupabaseSearch`, `useNCKPI`, `useNCDateTrend`. The functions they call were dropped.
- `chart.jsx` uses `dangerouslySetInnerHTML` for a style block built from config, not user input. No other
  HTML injection sink was found; an HTML title on an NC is stored as text.
- Local dependencies were out of step with the lockfile after updating the branch (the API would not compile
  until `npm install`). Not a product issue; worth knowing for new checkouts.
- Two migrations are noted in `CLAUDE.md` as not applied live (`20260105100000`, `20260106100000`), while the
  API on `Dev` selects their columns. Confirm before the next deployment.
- The billing gate is still off, by design. The Stripe path has not been run against Stripe.
