# Audits — plan (Documentation module)

**Status:** agreed (A1–A3 answered 2026-11-08, A4–A8 as proposed) · **Date:** 2026-11-08 · **Branch:** `Dev` · **Brief:** `docs/design-brief.md` §6.6, Phase 4

An **audit section** in the Documentation module. The quality team **defines** audits (what is checked, by what procedure, on which machines or
areas, how often and by whom), a **schedule** shows what is coming up, what was done and what was **missed**, and two registers list the
**audit definitions** and the **audit records** (each time an audit was actually carried out, with its result).

## 1. Words

| Term | Meaning |
|---|---|
| **Audit** (definition) | A repeatable audit: "Layered process audit — CNC cell", with its procedure, checklist, what it covers, how often and who does it. Register: **Audits**. |
| **Occurrence** | One slot in the schedule: this audit, for this machine (or area), due on this date. Created from the definition's frequency. |
| **Audit record** | One audit actually carried out: who, when, against which machine, the answer to every checklist question, the result (pass / fail) and what was found. Register: **Audit records**. |
| **Finding** | A question answered "fail" (with a note). A finding can be turned into a non-conformance on request, never silently. |

## 2. Proposed behaviour

### 2.1 Defining an audit (quality team, `audits.manage`)
- Code `AUD-001` (numbered per organisation), title, **type** (process, product, system, supplier, housekeeping/5S, layered process audit, other), purpose.
- **Procedure**: the written steps (rich text) and optional attached files, so the auditor knows how to do it.
- **Checklist**: ordered questions, each with guidance, an answer type — **pass / fail / not applicable**, **yes / no**, **number within limits** (with unit) or **text** —
  and a **critical** flag. Editing a definition never changes audits already done: a record keeps a **frozen copy** of the questions it was done against.
- **Relevant to**: a list of **machines** and/or **operations** (operation codes from the control plans) and/or departments. The audit is one schedule slot; the **record** says which of those it was carried out on (one or several, at least one).
- **Frequency**: daily, weekly, monthly, quarterly, every six months, yearly, **every N days**, or **on demand** (no schedule). A **first due date**, a **grace period**
  (days after the due date before it counts as missed) and optionally "weekdays only".
- **Who**: a named person, a role or a department. Whoever is named is the expected auditor; others with `audits.perform` may still do it (A3).
- Rules: **pass mark** — every critical question must pass, and the score (passes ÷ answered, N/A excluded) must reach a percentage (default 100%) (A2).
- Status active / retired (never deleted; retiring stops new occurrences and keeps the history).

### 2.2 The schedule (everyone with `audits.read`)
A page that opens from **Documentation → Audits → Schedule** with:
- **Upcoming** (due in the next N days, today highlighted), **Overdue** (past due, still inside the grace period), **Missed** (past the grace period with no audit), and **Done**
  (with the **pass / fail** result and a link to the record).
- Counts at the top: due this week, overdue, missed this month, on-time rate, pass rate.
- Filters: audit, machine, department, auditor, period, status. A **Start audit** button on every open slot (and "Start an unscheduled audit" for any definition).
- Calendar view (month) as well as the list.
- Occurrences are **generated by the API when the schedule or a definition is opened** (no worker): idempotent, a few weeks ahead, and past slots are never rewritten,
  so missed audits stay visible as history. An occurrence can be **skipped with a reason** (machine down, shutdown) by `audits.manage`; skipped slots do not count as missed.

### 2.3 Carrying out an audit (`audits.perform`)
Start from a schedule slot (or unscheduled) → the checklist opens, frozen from the definition → answer each question, add notes, attach photos → **Complete**.
The database works out the result from the answers and the pass mark and stamps who and when; a completed record is frozen (corrections are a new record, or a note
added with a reason). A fail asks for a note on each failed question. From a failed question the auditor can **Raise NC** (a draft internal NC linked to the record,
prefilled, never silent — the same pattern as inspections).

### 2.4 The two registers
- **Audits** (definitions): code, title, type, relevant machines/operations, frequency, who, last done, next due, last result, status. Filter and sort on the server, column config, URL filters.
- **Audit records**: reference `AR-26-0001`, audit, carried out on (machines / operations), auditor, scheduled for, performed on, result, score, failed questions, status; filters for
  audit, machine, operation, auditor, result, status, dates. Row opens the record.

## 3. Data (all tenant tables: RLS, audit trigger, no deletes, guardrails and both sweeps)

| Table | Purpose |
|---|---|
| `audit_definitions` | The audit: code, title, type, purpose, procedure, frequency (kind + interval), first due date, grace days, weekdays only, auditor (person / role / department), pass mark, status. |
| `audit_questions` | The checklist of a definition (sequence, text, guidance, answer type, limits, unit, critical). |
| `audit_targets` | What a definition is relevant to: a machine, an operation code or a department (one row each). |
| `audit_occurrences` | Schedule slots: definition, due date, status scheduled / skipped (reason); done and missed are derived from records and dates. Unique per (definition, due date). One slot per audit per period. |
| `audits` | The record: reference, definition, occurrence (optional), auditor, started / completed, status in progress / completed / abandoned (reason), result pass / fail, score. |
| `audit_record_targets` | What the record was carried out on (one or more of the definition's machines / operations / departments; a frozen label is kept). |
| `audit_record_questions` | The frozen copy of the checklist for that record (like `resolved_inspection_requirements`). |
| `audit_responses` | The answers (insert-only; corrections with a reason). |
| `audit_attachments` | Evidence files on a record (private `audit-files` bucket). |
| `audit_ncr_links` | Failed question ↔ NC raised from it. |

Lifecycle steps are SECURITY DEFINER functions (`app.start_audit`, `app.complete_audit`, `app.generate_audit_occurrences`, `app.skip_audit_occurrence`,
`app.raise_ncr_from_audit`), as for inspections and quality alerts. Error code `QM018` → `409 audit_rule`.

## 4. Permissions (named `audits.*` because `audit.read` is already the audit-trail permission)

`audits.read` (everyone who can read documentation or inspections), `audits.manage` (define, retire, skip a slot: owner, admin, quality manager, quality engineer),
`audits.perform` (carry out an audit: those plus inspectors and supervisors). Site-scoped through the target. Not subscription-gated (as production).

## 5. Slices

- **AU1 — definitions (built; migration `20251213100000_audit_definitions.sql`, not applied live yet):** migration (definitions, questions, targets, permissions), API, **Audits register** and the definition form (procedure, checklist builder, covers, frequency, who, pass mark). Menu group "Audits" under Documentation.
- **AU2 — schedule (built; migration `20251214100000_audit_schedule.sql`, not applied live yet):** occurrences and generation, skip, API, **Schedule page** (upcoming, overdue, missed, done, counts, calendar, filters).
- **AU3 — carrying out and records (built; migration `20251215100000_audit_records.sql`, not applied live yet):** start, frozen checklist, responses, complete with the computed result, **Audit records register**, record page; Raise NC from failed answers. Evidence files: **not built** (see §9).
- **AU4 — exit check:** live guardrails and advisors, browser journey (define → schedule → miss one → do one → fail one → NC), exit report, CLAUDE.md. Notification for "assigned to you" only if time allows; reminders by email are a later phase.

## 6. Decisions to confirm

| # | Question | Proposal |
|---|---|---|
| A1 | A definition lists several machines or operations. | **Answered:** the audit lists the machines / operations it is relevant to; it is **one slot per period** and the **record selects which of them it was carried out on** (one or several). The schedule and the register also show which listed machines/operations have **not been covered recently**. |
| A2 | When does an audit pass? | **Answered:** every **critical** question passes **and** the score reaches the definition's pass mark (default 100%). |
| A3 | Who may carry out an audit? | **Answered:** anyone with `audits.perform`; the named auditor is the expectation and is shown, not enforced. |
| A4 | How is the due date worked out after a slot is done late? | **Fixed calendar slots** (due dates stay on the original rhythm); a late audit completes its slot and the next slot is unchanged. |
| A5 | Definitions: revisions? | **No revision workflow now**: edit freely (audited); records keep their frozen copy. |
| A6 | Findings | A failed question is the finding. NC on request; **no separate findings or actions register yet** (Phase 4 later). |
| A7 | Reminders | **Computed, in-app** (the schedule and a menu count of overdue audits); no email or push yet. |
| A8 | Not in this section | Audit programmes across years, external/customer audits with certificates, scoring weights per question, auditor competence checks. |

## 8. AU2 built (schedule)

Migration `20251214100000_audit_schedule.sql`: `audit_occurrences` (one slot per audit per due date, `scheduled` | `skipped` only; **done, overdue and missed are worked out, never stored**; read-only for everyone, audited), `app.generate_audit_occurrences(org, until)` (idempotent, run by the API
when the schedule or the audits register is read, **no worker**; never before the audit existed, at most 120 days back and a year ahead; weekdays-only moves a weekend slot to the Monday; month-end clamping is worked out from the *first* due date, so 31 January → 28 February → 31 March;
a changed rhythm, a retired audit or an on-demand audit removes only future *scheduled* slots that have no record, past and skipped slots are history), `app.skip_audit_occurrence(id, reason)` / `unskip_audit_occurrence` (`audits.manage`; a slot with a record cannot be skipped).
API `GET /audit-schedule?from&to&state&auditId&machineId&operationCode&departmentId` (default window 30 days either side; slots, counts, `truncated` at 500), `POST /audit-occurrences/{id}/skip|unskip`.
State order: skipped, done (completed record), in progress (record started), else by date: upcoming (due today or later), overdue (past due, inside the grace period, last day included), missed (after it).
Counts: due in 7 days, in progress, overdue, missed, done (passed / failed), skipped; **pass rate** = done audits that passed ÷ done; **on-time rate** = of the slots decided in the window (done or missed), the share done by the due date plus grace (skipped, upcoming, in progress and overdue slots are left out).
UI: **Documentation → Audit schedule** (`/Documentation/Audit-Schedule`, `AuditSchedulePage.jsx`): the figures are buttons that filter the list by state, list and **month calendar** (Monday first, a slot opens a dialog with its actions), month navigation, audit and machine filters, URL `view|month|state|audit|machine`,
**Start audit** (`audits.perform`), **Skip** with a reason and **Put back** (`audits.manage`), **Start an unscheduled audit**.

## 9. AU3 built (records)

Migration `20251215100000_audit_records.sql`: `audit_records` (`AR-YY-NNNN` per organisation and year; a **frozen copy** of the audit's title, procedure and pass mark; one non-abandoned record per slot; in progress | completed | abandoned), `audit_record_questions` (the checklist as it was when started),
`audit_record_targets` (**which of the audit's machines, operations and departments it was carried out on, one or several**; a label is kept), `audit_responses` (one per question; the database works out pass / fail / not applicable), `audit_ncr_links`. **No INSERT, UPDATE or DELETE grant on any of them:**
every write is a SECURITY DEFINER function — `app.start_audit(audit, slot?, targets?)`, `set_audit_record_targets`, `record_audit_response` (yes/no by the passing answer, a number by its limits, both ends passing; clearing an answer is allowed while in progress), `update_audit_record` (notes, date not in the future),
`complete_audit`, `abandon_audit(reason)`, `raise_ncr_from_audit` — all needing `audits.perform` (the last needs `ncr.create` instead) and refusing a record that is no longer in progress. `app.audit_record_problems` is the "still needed" list: every scored question answered (a note question is not required), a note on every failure,
and the "carried out on" chosen when the audit lists anything. **Result:** score = passes ÷ (passes + fails), not applicable left out (no scored answers: no score, a pass); **fail if any critical question failed or the score is below the pass mark**, else pass. A completed record is frozen. A failed answer can be raised as a **draft internal non-conformance** (site from the machine, one live NC per
failed answer; a deleted or cancelled NC frees it), never silently. Errors `QM018` → `409 audit_rule`.
API `api/src/audits/audit-records.*`: `GET /audit-records` (page-based: `q`, `auditId`, `status`, `result`, `type`, `machineId`, `operationCode`, `departmentId`, `performedBy` (who completed it, else who started it), `mine`, `from`, `to`, `sort`, `order`, `page`, `pageSize`), `POST /audit-records {auditId, occurrenceId?, targets?}`, `GET|PATCH /audit-records/{id}`,
`PUT …/targets`, `PUT …/responses {questionId, answer?, value?, note?}`, `POST …/complete|abandon|raise-ncr`. The audits register and page now also carry `lastRecord` and `nextDueOn` (the next slot that is due today or later, or past due but inside its grace period, with no audit started and not skipped).
UI: **Audit records register** (`/Documentation/Audit-Records`, `AuditRecordsPage.jsx`, same table pattern as the other registers; filters audit, result, status, machine, dates, "only audits I did"), **record page** (`/Documentation/Audit-Records/:id`, `AuditRecordPage.jsx`: answers saved as they are given and shown at once, put back if the save fails;
what it was carried out on; what is still needed; Complete; Abandon; the result banner; Raise non-conformance), **Last done / Next due** columns on the Audits register and facts plus a **Start audit** button on the audit page.

**Not built (agreed to leave out of this slice):** evidence files on a record and files on the procedure (`audit_attachments`, an `audit-files` bucket), email or push reminders, a menu count of overdue audits (A7 named it; the schedule shows overdue and missed instead), corrections to a completed record (a new record is the correction), per-question weighting.
